## 五、已确定的产品方案

### 5.1 家长设置完成照片规则

在家长新建和编辑任务表单中增加分段选择控件：

标题：`完成时要拍照吗？`

三个互斥选项：

1. `可以拍一张`：默认值；孩子可以拍照，也可以不拍直接提交。
2. `必须拍一张`：没有照片不能提交。
3. `不用拍照`：保持原来的快速提交流程。

内部值可使用：

```js
photoPolicy: "optional" | "required" | "none"
```

要求：

- 新建任务默认 `optional`。
- 旧任务迁移后默认 `none`，避免历史行为被强制改变。
- 每日任务必须沿用当前“仅今天、明天起、今天和以后”的编辑范围规则。
- 修改拍照规则不能覆盖已经形成的历史记录。
- 任务管理列表显示孩子能看懂的状态，例如“拍照可选、需要拍照、不用拍照”。

### 5.2 孩子端完成流程

孩子点击“我完成了”后，打开完成弹窗。

弹窗必须包含：

- 任务名称。
- 家长写的任务要求。
- 家长任务提示图（如果有），标签为“要做什么”。
- 新的完成照片区域，标题为“给家长看看吧”。
- `拍一张`按钮，调用后置摄像头：`accept="image/*" capture="environment"`。
- `从相册选`按钮，不设置 `capture`。
- 选择后立即显示预览。
- `重新拍`、`换一张`、`删除`。
- 每次提交最多一张完成照片。

三种规则的交互：

- `none`：不显示照片区域，维持当前确认提交体验。
- `optional`：显示照片区域，并提供`暂时不拍，直接提交`。
- `required`：没有选好照片时禁用最终提交按钮，并显示“拍好照片后就能提交啦”。

提交状态：

- 选择照片后先本地预览，不要立即产生正式任务记录。
- 用户点击最终提交后，显示“正在提交，请稍等”。
- 图片保存和任务状态更新必须作为一个完整流程处理。
- 只有图片保存和状态持久化都成功后，任务才进入“等待家长确认”。
- 任一步失败时保持任务为待完成或需要再完成，并允许重试。
- 不得出现“任务已提交但照片丢失”或“图片已保存但产生错误任务状态”。

提交成功文案：`已经告诉家长啦，等待确认吧`。

### 5.3 手机图片处理

复用并完善当前任务提示图的图片处理能力，但不要把孩子照片当作家长素材权限处理。

要求：

- 支持手机直接拍照和相册选择。
- 浏览器可以解码时，将 HEIC/HEIF、JPG、PNG、WebP 统一重新编码为 JPEG。
- 自动纠正常见手机照片方向，避免横竖颠倒。
- 最长边压缩到约 1600px。
- JPEG 质量建议 0.82-0.88，以清晰看清作业文字为准。
- 上传前重新编码，去除 EXIF 中的定位、设备等附加信息。
- 服务端最终图片建议不超过 6MB。
- 服务端必须根据文件真实签名校验格式，不能只相信扩展名或 Content-Type。
- 无法解码时使用儿童可理解的提示：`这张照片暂时打不开，请重新拍一张或从相册换一张`。
- 对象 URL 使用完后及时释放，避免移动端内存持续增长。

### 5.4 孩子端上传接口边界

当前 `/api/upload` 只允许家长使用，不能简单去掉鉴权或让孩子复用通用素材上传接口。

推荐新增专用、原子化的任务提交接口，例如：

`POST /api/task-submissions`

请求只允许包含：

- `taskId`
- 可选的完成照片数据

服务端必须：

1. 校验任务存在。
2. 校验任务当前状态只能是 `todo` 或 `redo`。
3. 校验该任务的 `photoPolicy`。
4. `none` 不接受完成照片。
5. `required` 没有有效照片时拒绝提交。
6. 每次只接受一张静态图片，不接受视频和任意素材。
7. 校验请求大小、真实 MIME、像素尺寸和上传频率。
8. 保存照片、创建提交尝试、更新任务状态并写入当天记录。
9. 任何步骤失败时删除本次临时文件并回滚状态。

不得因为孩子端可以提交任务，就开放一个无限制、可上传任意文件的公开接口。

## 六、数据模型与迁移

不要把完成照片放进现有 `guideImage`。

建议数据结构：

```js
task.photoPolicy = "none" | "optional" | "required";

task.submissionAttempts = [
  {
    id: "attempt-id",
    submittedAt: "ISO time",
    completionPhoto: {
      url: "/product/uploads/...jpg",
      thumbnailUrl: "/product/uploads/...jpg",
      mimeType: "image/jpeg",
      width: 1200,
      height: 1600,
      updatedAt: "ISO time"
    } | null,
    decision: "pending" | "confirmed" | "redo",
    decidedAt: "ISO time" | null,
    redoReason: ""
  }
];
```

可以根据现有代码模式调整字段，但必须满足：

- `guideImage` 永远表示家长任务提示图。
- `completionPhoto` 永远表示孩子某次提交的完成照片。
- 一次退回再提交必须形成新的 attempt，不能覆盖旧照片和旧处理结果。
- 当前待处理显示最后一次 `pending` attempt。
- `taskDayRecords` 必须保存当天 `photoPolicy` 和提交尝试快照。
- 每日任务进入新一天时，当前提交尝试清空，但昨天记录完整保留。
- 一次任务确认后保留只读记录。
- 旧的 `submittedAt`、`confirmedAt`、`redoReason` 如需保留兼容，必须有清晰迁移规则，不能出现两个来源相互矛盾。

将数据结构版本从 4 升级到新的版本。迁移必须幂等，并覆盖：

- 旧 `taskDayRecords`。
- 重启后再次执行迁移。
- 数据字段缺失或部分存在的情况。

上传引用检查 `hasUploadReference` 必须覆盖：

- 任务提示图。
- 数字奖励素材。
- 现实奖励图片。
- 当前任务完成照片。
- 每日任务历史记录中的完成照片。
- 所有提交尝试中的历史照片。

## 九、异常与边界逻辑

必须覆盖：

1. 相机权限被拒绝：仍可从相册选择；可选模式仍可无图提交。
2. 必须拍照但设备无法拍照：提示从相册选择，不能静默绕过规则。
3. 图片过大：先自动压缩；仍超限时给出可理解提示。
4. 图片方向错误：重新编码后保持正确方向。
5. 网络中断：任务状态不改变，照片预览保留到用户重试或关闭。
6. 用户重新拍摄：只保留最终选择，及时清理对象 URL 和未引用临时数据。
7. 快速重复点击提交：必须防抖并在服务端防止重复 attempt。
8. 任务已经被家长处理时再次提交：服务端拒绝并刷新最新状态。
9. 家长确认重复请求：不得重复发星币。
10. 退回后重新提交：形成新 attempt，旧照片和退回原因可查看。
11. 每日任务跨天：昨天照片只保存在昨天记录，今天从空状态开始。
12. 浏览器刷新、服务重启和 Docker 重建后：图片与记录仍然存在。
13. 图片文件不存在或损坏：页面不崩溃，显示清晰占位。
14. 历史任务标题、奖励或要求后来修改：历史记录继续显示当时快照。

## 十、视觉与响应式要求

沿用现有聿宝星球家长端安静、清晰、工作型视觉，不重新设计品牌和素材风格。

要求：

- 不生成新的装饰性图片。
- 不使用大面积色块堆叠或营销式页面。
- 不在卡片里再套卡片。
- 图片区域必须设置稳定宽高比，加载前后不能挤压页面。
- 完成照片使用 `object-fit: contain`，不能裁掉作业内容。
- 缩略图可适度裁切，但进入详情后必须完整显示。
- 所有状态不能只靠颜色区分，必须有文字。
- 图标和文字垂直对齐。
- 按钮文字不能溢出或重叠。
- 左侧导航、页面标题、详情抽屉和底部操作区不能互相遮挡。
- 尊重安全区域 `env(safe-area-inset-*)`。
- 不随 viewport 宽度任意缩放字体。

至少验收以下视口：

- 1440x900 桌面。
- 1280x800 桌面。
- 1024x1366 iPad 竖屏。
- 1366x1024 iPad 横屏。
- 390x844 iPhone。
- 412x915 Android。

重点检查：

- 家长端待处理卡片信息完整且不拥挤。
- 右侧详情抽屉在桌面不压缩到不可读。
- 移动端详情底部按钮不遮挡图片和时间线。
- 孩子完成弹窗的拍照、相册、预览和提交按钮不重叠。
- 横竖图均可完整查看。

## 十一、无障碍与可用性

- 所有图片按钮需要清晰的 `aria-label`。
- 完成照片大图查看器支持 Esc 关闭、焦点管理和遮罩点击关闭。
- 弹窗或抽屉打开后焦点进入标题或首个可操作控件，关闭后回到原触发按钮。
- 键盘可以完成查看详情、切换记录标签、打开图片和处理任务。
- 文件选择控件必须有真实 label，不能只有图标。
- 上传中按钮禁用，并通过 `aria-live` 反馈状态。
- 可见焦点不能被移除。
- 不从截图单独声称完全符合无障碍标准；需要实际键盘和焦点测试。

## 十二、自动化测试要求

在现有测试之外新增专门测试，例如：

- `tests/task-completion-photo-api.mjs`
- `tests/parent-task-records-api.mjs`

必须覆盖：

### 任务拍照规则

- 旧任务迁移后为 `none`。
- 新任务默认 `optional`。
- `none` 无图可提交，带图被拒绝或明确忽略，行为必须固定并测试。
- `optional` 有图、无图均可提交。
- `required` 无图不能提交，有合法图可以提交。

### 上传安全

- 伪造扩展名。
- MIME 与真实内容不一致。
- 非图片文件。
- 超出大小。
- 无法识别尺寸。
- 无效 taskId。
- 非待完成状态上传。
- 重复提交。
- 临时文件回滚。

### 任务状态

- 提交后进入 pending。
- 家长确认后只发一次星币。
- 退回后旧 attempt 标记为 redo。
- 重新提交生成新 attempt。
- 历史照片不被新照片覆盖。
- 每日任务跨天不沿用照片。
- `taskDayRecords` 保存当日完整快照。

### 数据持久化

- 服务重启后照片、attempt、记录仍在。
- 多次迁移结果一致。
- 清空使用记录删除完成照片，但不删除仍被任务提示图或奖励引用的素材。

### 家长端展示

- 待处理使用完成照片，不使用任务提示图冒充。
- 无完成照片显示“未附照片”。
- 所有任务状态都有查看详情。
- 任务记录、奖励兑换、星币账本三个标签均可使用。
- 历史详情显示快照和完整时间线。

### 回归

- 家长任务提示图新建、编辑、预览和每日任务范围规则继续通过。
- 数字奖励与现实奖励功能继续通过。
- 星币余额、冻结、确认发放和兑现逻辑继续通过。
- 孩子装扮的 `currentOutfit/currentTheme/currentPet` 或现有等价字段不受影响。

更新 `package.json` 的 `npm test`，使其执行全部回归测试，而不是只运行一个测试文件。不得为了通过测试删除原测试。

## 十三、真实浏览器验收

完成代码后启动一个不占用现有服务端口的新本地服务，并使用隔离数据目录。

必须真实走通：

1. 家长创建“必须拍照”的任务，并添加任务提示图。
2. 孩子端查看“要做什么”。
3. 孩子拍摄或选择完成照片，预览并提交。
4. 家长首页看到完成照片缩略图。
5. 家长待处理看到完整信息并打开任务详情。
6. 家长要求再完成并填写原因。
7. 孩子看到原因，重新提交新照片。
8. 家长在详情中看到两次提交和两张对应照片。
9. 家长确认完成，星币只增加一次。
10. 任务记录中出现当天完整记录。
11. 星币账本仍有正确流水。
12. 重启服务后再次打开，记录和图片仍存在。

浏览器验收必须截图并检查，不得只看 DOM 或测试返回值。截图应保存在 `/private/tmp` 或项目明确的临时 QA 目录，不要把大量 QA 截图提交进仓库。
